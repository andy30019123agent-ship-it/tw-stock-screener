# 前端審查報告 — tw-stock-screener

審查範圍：`src/`（React + Vite 前端）。正確性、手機效能、資訊呈現、無障礙。
不含後端統計正確性與部署鏈（歸另一 agent）。**唯讀審查，未改任何程式碼。**

驗證方式：
- `npm run build` 實跑一次；用 scratch 副本（複製到暫存目錄，非本 repo）拆掉 `StockChartModal` 再 build 一次量測 bundle 差額。
- `node` 直接讀 `public/data/screener.json`（925 檔、56 欄／檔）與 `signal_weights.json` 算欄位分布、樣本數。
- headless Chrome CDP `Emulation.setDeviceMetricsOverride{width:390,mobile:true}` 實測首頁、篩選面板、戰績表格三個畫面，含截圖與 a11y snapshot。
- WCAG 對比度用 node 手算相對亮度（sRGB relative luminance）驗證 design token 配色。

## 🔴 嚴重（2 個）

### 1. 快速套用排序無視樣本外驗證，「填息快」樣本不足卻排最前、字最大
**檔案**：`src/components/ConditionPanel.jsx:49-52`（`presetScore`）、`:96-99`（`orderedPresets` 排序）

`presetScore` 只拿 `avg_excess`（平均超額報酬）排序快速套用 chip，完全不看同一資料裡就有的 `oos.status`（樣本外穩健度）。實測 `signal_weights.json`：`fill_fast`（填息快）`avg_excess=3.27pp` 但 `oos.status="insufficient_oos"`（樣本外資料不足，無法驗證是否真的有效），卻因為數字最大被排到 chip 第一顆、字級最大、顏色最搶眼。390px 手機截圖已確認：「填息快 +3.27pp」排在「多頭排列 +1.03pp（穩健）」「小詩選股 +0.77pp（穩健）」之前。使用者若只看 chip 不點開下方「各策略回測戰績」表格，會誤以為填息快是目前最強策略，但表格裡它的樣本外欄位其實寫「資料不足」。這是本站對投資決策風險最高的一處：最顯眼的位置放了驗證度最弱的數字。
**修法**：`presetScore` 加入 OOS 懲罰（例如非 `robust`/`regime_specific` 就打折或直接不參與排序，只依原始清單順序排在後段），或至少在 chip 上加一個小標記（灰點／⚠️）呼應下方表格的徽章，別讓排序純粹被未驗證的數字牽著走。

### 2. `ResultTable` 手機/桌機兩份完整 DOM 同時渲染 + 每次篩選強制整表重建
**檔案**：`src/components/ResultTable.jsx:101-211`（`.card-list` 與 `.table-wrap` 皆無條件渲染，靠 CSS `display:none` 切換）、`src/App.css:664,817-818`、`src/App.jsx:233`（`key={`${sortKey}:${filtered.length}`}`）

`ResultTable` 對每檔股票同時 `.map()` 出「手機卡片」與「桌機表格列」兩份完整節點（各自含一顆 `Sparkline` SVG），只用 CSS `display:none` 決定顯示哪份——兩份都在 DOM 裡、都要 React 建立/diff。放寬篩選看到接近全部 925 檔時，等於同時撐著 1850 個列項（含 1850 顆 sparkline polyline）在記憶體與版面樹裡，其中一半永遠不會被看到。
更嚴重的是 `App.jsx:233` 的 `key={`${sortKey}:${filtered.length}`}`：只要任何條件切換改變命中檔數（幾乎每次都會），這把 key 就會變，逼 React **整個 `ResultTable` 卸載重掛**，而不是用既有的 `key={s.id}` 做局部 diff——本來 90% 相同的股票列表，變成每次操作都從零重建兩份、共上千個節點。今天預設條件命中僅 3 檔看不出來，但只要 Andy 放寬到「多頭排列」單一條件（實測 113 檔）或全部展開（925 檔），每次點選條件都會有感卡頓。
**修法**：① 用 `matchMedia` 或現有的 `dense`/斷點邏輯二選一渲染，別兩份都塞進 DOM；② 拿掉 `key={sortKey:filtered.length}`，讓 `stocks.map(s => ... key={s.id})` 自己做增量 reconciliation（若原本是為了修某個排序後殘影的 bug，改成只在 `sortKey` 變時強制、或直接查那個 bug 的根因）。

## 🟡 中等（4 個）

### 3. `lightweight-charts` 未 code-split，佔首屏 JS payload 46%
**檔案**：`src/components/StockChartModal.jsx:2`（`import { createChart, LineStyle } from 'lightweight-charts'` 是靜態 import）、`src/App.jsx:5`

實測：`npm run build` 完整版 JS 是 371.57 KB（gzip 121.30 KB）；用 scratch 副本拿掉 `StockChartModal` 的 import/使用後重 build，降到 201.29 KB（gzip 65.64 KB）。差額 170.28 KB／gzip 55.66 KB 全部是 K 線圖表庫，**每個訪客只要打開首頁就要下載＋解析，即使他從沒點開任何一檔的 K 線彈窗**。首次造訪或 iOS Safari 清快取後這筆成本都要重付一次。
**修法**：`StockChartModal` 改 `React.lazy` + `import()` 動態載入，外面包一層輕量 `Suspense` fallback（例如點卡片先顯示 loading 骨架，再載入圖表模組），只有真的點開股票才付這筆成本。

### 4. 戰績表格內「樣本外」徽章顏色語意與同列其他欄位相反
**檔案**：`src/App.css:334-335`（`.preset-score.good`＝`--up`紅、`.bad`＝`--down`綠）對比 `:357-359`（`.oos-badge.oos-robust`＝`--down`綠、`.oos-bad`＝`--up`紅）

站內「紅涨綠跌」的延伸用法是「好=紅（--up）、壞=綠（--down）」，`平均超額`、`成本後期望`、組合戰績、機會股成績單全部照這個規則（已用 390px 截圖驗證：正的平均超額欄位顯示紅字）。但**同一張表、同一列**的「樣本外」欄位剛好相反：`穩健`（好消息）用綠色徽章、`過擬合`（壞消息）用紅色徽章——螢幕截圖已實拍確認。文字本身（"穩健"／"資料不足"）不會讓人誤讀，但色彩這條「一眼判斷」的捷徑在同一列被打斷，容易讓快速掃視的人把「樣本外＝綠」誤讀成跟其他欄位一樣「差」。
**修法**：把 `oos-robust` 改用 `--up`（紅／好），`oos-bad` 改用 `--down`（綠／壞），跟同一列其餘欄位的紅=好、綠=壞對齊。

### 5. 部分紅/綠語意色文字未達 WCAG AA 對比度
**檔案**：`src/App.css:284-285,334-335,357-360` 等所有引用 `--up`/`--down` 當文字色的地方

手算 sRGB 相對亮度對比度（AA 一般文字門檻 4.5:1）：
- `--down`（#0F8A5F 綠）在白底：4.36:1（不足）
- `--down`（#0F8A5F 綠）在 `--down-bg`（#E7F4EE）底（oos-badge 用）：3.85:1（明顯不足）
- `--up`（#D0303C 紅）在 `--up-bg`（#FBE9EA）底：4.30:1（不足）
- `.oos-badge.oos-warn` 文字 `#9A6A00` 在 `#FBF0D8` 底：4.18:1（不足）
- 對照組：`--up` 紅在白底 5.04:1（過關）、`--ink-muted` 在白底 5.40:1（過關）

這些是介於 3.85~4.30 之間的邊緣不足，非重度看不清，但用在「平均超額」「成本後期望」等關鍵決策數字上，值得順手修。
**修法**：`--down` 加深至接近 `#0C7A52`、`--up` 在 tint 背景可維持原值只加粗字重或加深 tint 底色，讓文字色對比回到 4.5:1 以上。

### 6. `.oos-badge.oos-warn` 使用裸 hex，未走 design token
**檔案**：`src/App.css:358` — `color: #9A6A00; background: #FBF0D8;`

`design-system/MASTER.md` 的「元件禁裸 hex」鐵則在這一行被破了（同檔案其餘顏色都走 `var(--xxx)`）。使用者看不出來，但下次全站調色（例如上面第 5 點要調對比度）這行會被漏掉。
**修法**：補一個 `--warn`/`--warn-bg` token 到 `:root`，這裡改吃 token。

## 版面／無障礙補充（390px 實測，未見更嚴重問題）
- 首頁到條件面板到戰績表格全程 `document.documentElement.scrollWidth === window.innerWidth === 390`，**無橫向溢出**。
- 寬表格（`strategy-table`／`combo-table`／`opp-weights-table`）都包在各自 `overflow-x:auto` 容器裡，桌機專用的 `.result-table`（`min-width:860px`）在 ≤720px 用 `display:none` 正確隱藏。
- 觸控目標多數落在 44×44px（`min-height:44px` 隨處可見）；少數如 `.density-btn`／`.combo-clear`（36-40px）略低於 44px 但仍在 WCAG AA 24px 底線之上，非阻斷級問題。
- `.cond-toggle`（ConditionPanel 內建的摺疊標題鈕）在所有斷點都是 `display:none`（`App.css:303-306` 未被任何 media query 覆寫成可見），是有意的死碼——手機開合已交給 `App.jsx` 的 sticky 工具列「篩選」鈕代管，桌機恆展開不需要它。目前沒有副作用，只是留意未來別誤删 `App.jsx` 的工具列鈕以為這個內建鈕還在運作。

## 優化方案（5 個，依「對 Andy 的實際價值 ÷ 實作成本」排序）

1. **快速套用排序納入 OOS 穩健度**（對應發現 1）——`ConditionPanel.jsx` 的 `presetScore` 加一段「非 robust 打折/降權」邏輯，或 chip 上補小圖示呼應下方表格徽章。改動集中在一個函式，風險低，直接消除本站目前最大的「數字誤導」風險。
2. **`StockChartModal` 改 lazy load**（對應發現 3）——`React.lazy(() => import('./components/StockChartModal'))` + `Suspense`，首屏 JS 少 46%（實測 170KB/55.66KB gzip）。改動集中在 `App.jsx` 一處 import，風險低，Andy 手機首次載入／清快取後最有感。
3. **`ResultTable` 拿掉強制 remount、二選一渲染桌機表格或手機卡片**（對應發現 2）——移除 `key={sortKey:filtered.length}`、用既有的 `dense`/斷點判斷只渲染其中一份 DOM。改動範圍稍大（`ResultTable.jsx` + `App.jsx` 各一處），但是全站唯一會在「放寬篩選看更多檔」時真的卡頓的地方。
4. **修正 oos-badge 紅綠語意方向 + 補 `--warn` token**（對應發現 4、6）——兩行 CSS 顏色對調、一個 token 補齊，純視覺、零邏輯風險。
5. **加深 `--down` 綠色，補足 WCAG AA 對比**（對應發現 5）——單一 token 改值，順手驗證不會跟現有截圖的視覺風格衝突即可。

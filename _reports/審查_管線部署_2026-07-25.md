審查日期：2026-07-25（台北）

## 一、發現清單

### 🔴 1. 每日累積路徑沒有「單日筆數異常」防呆——build_universe.py 有，daily_update.py 沒有
**檔案**：`pipeline/daily_update.py:35-60`（對照 `pipeline/build_universe.py:85-94` 的 70% 防呆）

**情境**：TWSE `STOCK_DAY_ALL` 回應途中被截斷、或某天只回傳半份表格（非空、非 None，
只是筆數大幅減少，例如從 ~1000 檔掉到 300 檔）。`fetch_listed_ohlc_latest()` 仍會回傳有效
`date_iso` 和非空 dict，`daily_update.py:42` 的 `if not date_iso or not listed` 檢查**完全不會
觸發**——因為 dict 非空。於是這份殘缺資料直接 `hs.append_price()` 寫進 `price.json` 並
`write_fetch_state(True)`，前端顯示「已更新、非過期」，但實際上多數股票當天**沒有新的一筆
K 線**（不是崩潰，是悄悄變薄）。`build_universe.py` 已經證明開發者知道這個風險（清單少三成
就不覆寫），但同一套防呆沒有套用到每天真正寫入歷史的 `daily_update.py`（上市/上櫃 OHLCV、
法人 chip 皆無此檢查）。`backfill_bt.py:66-68` 同理，只防「兩邊都空」，不防「單邊部分」。

**修法**：`daily_update.py` 抓到 `listed`/`otc` 後，比對 `price.json` 前一交易日的股票數
（或 `universe.json` 的 `count`），少於七成就視同抓取失敗、`write_fetch_state(False)` 並跳過
寫入（沿用既有歷史），複用 `build_universe.py` 已寫好的邏輯即可。

### 🔴 2. 已經在生產歷史裡的「假 0 元」污染（非假設，已用真實資料驗證）
**檔案**：`pipeline/market_sources.py:63-71`（`_f()`）與 `:101-106`（`_ohlc()`）

**已發生的實際案例**（掃描 `pipeline/history/price.json` 全部 110 天）：
`1213`（2026-07-16/17/20）、`1341`、`1538`（多次）、`2254`、`2321`、`2438` 等
**至少 8 檔股票、36 筆日期**出現 `open=high=low=close=0.0`，但同一天 `Trading_Volume`／
`Trading_money` 是非零小額（例：`1213` 2026-07-16：`[0.0,0.0,0.0,0.0, 1股, 7元]`——
成交金額 7 元、量 1 股，換算單價明明是 7 元，卻被記成收盤 0）。

根因：`_f()` 只把 `"--"/"X"/"N/A"` 等字串視為無效值 → None，但把字串 `"0.00"`
當成合法浮點數 0.0（TWSE 對零股/極低量成交似乎會回傳 `"0.00"` 而非 `"--"`）。
`_ohlc()` 的空值檢查 `if None in (o,h,lo,c)` 因此攔不到這種「格式對、內容錯」的列，
整批寫進歷史，沒有任何警告或 log。**這不是理論風險，是目前 `main` 分支已經 commit
回去的真實資料**，會餵給下游均線/突破/乖離率等指標算出假訊號。`pipeline/tests/test_market_sources.py`
也沒有涵蓋 `_f("0.00")` 這個案例（第 22-25 行只測 `--`/空字串）。

**修法**：`_ohlc()` 加一條 `close <= 0` 視為無效（丟棄該列，如同 None 處理）；
補一條測試 `assert ms._f("0.00")` 搭配 `_ohlc` 對 close=0 的行為。

### 🟡 3. 大額跳空缺乏「除權息事件」比對防呆，價格斷點無感知機制
**檔案**：`pipeline/market_sources.py:242-287`（`fetch_ex_dividend_events`，只吃 TWSE `TWT49U`
／TPEX `exDailyQ_result.php`，即一般現金/股票股利除權息）

**已發生的實際案例**：`3086`（2026-04-20，325→35.75，-89%）、`2380`（2026-06-29，6.6→21.5，+226%）、
`3152`（2026-06-30，208→324.5，+56%）、`8932`（2026-03-09，199.5→89.8，-55%）、
`8937`（2026-04-13，145.5→38，-74%）——皆為**持續性**跳空（非單日反彈的髒點），符合
「現金減資」等特殊事件特徵，但 `pipeline/history/dividends.json` 對這 5 檔**完全沒有對應
事件記錄**（`TWT49U`/`exDailyQ` 這兩個端點涵蓋不到減資調整）。歷史序列因此帶著未還原的
價格斷點，且**沒有任何機制標記**「這裡有一段落差抓不到對應除權息事件」——下一次 build 時
均線/乖離率會把它當成真實暴漲暴跌。這是資料完整性缺口，不動下游計算公式（那是另一個
agent 的範圍），但屬於本管線該負責的「有沒有機制感知資料斷點」。

**修法**（低成本版）：daily_update.py 或每週維護腳本加一條「單日漲跌幅 > 30% 但當天/前一
交易日查無除權息事件」的規則式警告，寫進 log 或推播提醒人工核對，不用真的處理減資邏輯。

### 🔴 4. Workflow 失敗（含 git push 衝突）沒有任何主動通報
**檔案**：`.github/workflows/daily.yml:93-108`（commit/push 步驟）、`:110-123`（build/deploy，
兩者皆無 `if: always()` 或失敗通知步驟）

**情境**：`concurrency` 群組只序列化本 workflow 內部的排程/手動觸發，**不保護對 Andy 從本機
直接 `git push` 到 main 的情況**——例如今天這種在 Claude Code session 裡改前端程式碼並直接
push 到 main，若時間點正好落在某次 workflow 執行到「保存歷史與紀錄回 main」這步之間，
`git push origin HEAD:main`（第 107 行）會因為 non-fast-forward 被拒絕、直接 fail，且**沒有
`git pull --rebase` 重試**。GitHub Actions 預設：這一步失敗後，後面「npm build」「部署到
GitHub Pages」都會被跳過（沒有 `if: always()`），代表**當天完全不部署、也不更新資料**。
唯一的訊號是 Actions 頁面一顆紅叉——GitHub 對排程失敗預設只會寄 email（若帳號有開通知），
**不會進 Andy 慣用看訊息的 Telegram/Discord**（違反鐵則 1 的精神但這是外部平台限制不是
本專案程式碼的鍋，仍該補一層通報）。使用者要等前端 `daysStale > 5` 天才會看到過期警告
banner——等於**最長 5 天內沒人知道自動化已經停擺**。

**修法**：在 workflow 最後加一個 `if: failure()` 的步驟，失敗時打 Telegram（沿用
`TG_BOT_TOKEN`）發一則「今日自動更新失敗，請人工檢查 Actions」的訊息；`git push` 前视情况
加 `git pull --rebase origin main` 重試一次再 push，降低誤殺率。

### 🟡 5. `.git` 持續肥大，`bt_price.json`（18MB）每天整檔改寫、delta 壓縮效率差
**驗證**：`.git` 目前已 135MB；`pipeline/history/bt_price.json` 18MB、`price.json` 11MB，
皆為 minified 單行 JSON，每天的增量寫入會讓整個檔案內容位移，git 的 delta 壓縮效果差，
等同每天新增一份接近全量大小的 blob。目前遠低於 GitHub 單檔 100MB 硬限制，但這條增長曲線
若持續（`bt_price.json` 未來擴充視窗、或新增更多欄位）會讓 clone/checkout 越來越慢，
每次 workflow 執行時間拉長，長期有觸及 GitHub 免費層 repo 容量軟限制的風險。目前**沒有
任何監控或警報**會在檔案接近危險大小前提醒。

**修法**：非急迫，列入季度檢查即可——例如加一條「`du -sh .git` 超過 500MB 就提醒」的檢查，
或評估把 `bt_price.json` 換成非 git 儲存（如 GitHub Release asset／外部物件儲存）。

### 🟢 6. 秘密與權限：目前配置正常，僅記錄現況
`TG_BOT_TOKEN`／`FINMIND_TOKEN` 皆透過 GitHub Secrets 注入環境變數（GHA 會自動遮罩
log 中出現的值）；git push／GitHub Pages 部署都用內建 `secrets.GITHUB_TOKEN`（scope 限
`contents: write`），沒有另外持有的 PAT 明文散落在 repo 或 workflow 裡；`finmind_dates`
輸入走 env 而非直接內插進 shell（已有防注入註解）。`FINMIND_TOKEN` 是以 URL query string
方式傳給 FinMind API（`finmind_fill.py:56-60`），這是 FinMind API 本身的設計慣例（GET 帶
token），非本專案可控，風險低，僅記錄。**無需修復動作。**

### 🟡 7. 時間戳記在 GitHub Actions runner 用 `datetime.now()`，等同 UTC，未來新功能容易踩雷
**檔案**：`daily_update.py:25`、`build_universe.py:81`、`build_data.py:717`、
`opportunities.py:151`、`backtest_signals.py:1080`、`monthly_revenue.py:67`——全部用
`dt.datetime.now().strftime(...)` 寫「updated/checked_at/computed/fetched_at」欄位，
GitHub Actions runner 是 UTC，等同這些欄位比台北時間慢 8 小時、且完全沒標時區。
**目前尚未造成使用者可見的錯誤**——前端 `App.jsx:73-77` 判斷過期用的是 `data.data_date`
（交易日字串，非受影響的時間戳）而非這些 `updated` 欄位。但這是個「隨時會因為新功能引爆」
的地雷：未來若想在網頁上顯示「資料於 XX:XX 更新」或用 `checked_at` 做任何鮮度比對，會直接
把 UTC 當台北時間顯示，讓人誤以為系統半夜更新或提早了 8 小時。

**修法**：低成本，統一改成 `dt.datetime.now(dt.timezone(dt.timedelta(hours=8))).strftime(...)`
或加註解「此欄位為 UTC，顯示前需自行 +8」，防止未來人（或 AI）誤用。

## 二、優化方案（依「防災價值 ÷ 實作成本」排序，限 5 個）

1. **daily_update.py 補上「單日筆數 70% 防呆」**（對應發現 1）——直接複製
   `build_universe.py` 已寫好的邏輯到 price/chip 累積前，成本最低（抄現成的），
   防的是「悄悄變薄卻顯示成功」這個本次審查裡最危險的一類問題。

2. **`_ohlc()` 加 `close <= 0` 視為無效**（對應發現 2）——一行判斷式 + 一條測試，
   立刻擋掉未來的假 0 元污染；建議同時寫一支一次性清洗腳本（人工跑、不進 workflow）
   把現有 36 筆 0 值從歷史裡剔除或標記，避免繼續污染回測樣本。

3. **Workflow 加 `if: failure()` 的 Telegram 失敗通報**（對應發現 4）——十幾行 YAML，
   直接補上這條鏈路唯一還沒有的「自動化本身掛掉，主動叫醒人」的能力，跟現有
   「資料抓取失敗要警告」的設計理念一致，只是把警告範圍從「資料層」擴大到「流程層」。

4. **大額跳空 + 無除權息事件的規則式警告**（對應發現 3）——用簡單門檻（如單日
   `|漲跌幅| > 30%` 且查無除權息事件）印一行警告到 workflow log（或順便推播），
   不用真的處理減資邏輯，成本低，換來「至少有人知道哪幾檔的歷史有斷點」。

5. **`.git`／`bt_price.json` 大小監控點**（對應發現 5）——workflow 裡加一步
   `du -sh .git` 超過門檻就在 log 印警告，季度回頭看一次即可，成本最低但目前
   急迫性也最低，排最後。

# 設計：漏抓交易日自動回補（2026-11-13）

## 一句話

以前每天只抓「今天」，哪天抓失敗那天就永遠空著；現在每天抓完後多做一件事——拿證交所官方的「這個月哪幾天有開盤」清單對照我們的歷史，少了哪天就回頭補抓，一次最多補 3 天，補不到的記下來隔天再試。

## 白話比喻

像記帳本：以前每天只記當天的帳，某天忘了就整頁空白。現在每晚記完，會翻開銀行對帳單（官方交易日清單）對一下最近 20 天，發現哪天空白就去把那天的收據（吃日期的全市場資料）找回來夾進正確的頁數，不是貼在最後一頁。找不到收據的那天不會亂填，只在便利貼上寫「待補」。

## 設計取捨

1. **「應有交易日」用 TWSE FMTQIK，不用 index.json。** 加權指數（index.json）是跟個股同一步抓的，每日那步失敗時它也一起缺——實際查過，08-18～08-20 index.json 同樣沒有。FMTQIK 是另一個端點，當天失敗不影響它事後列出那天；它還附當天加權指數收盤，順便補 index.json，不用多打請求（已比對 08-14、08-17、08-21、08-24 四天，跟 index.json 現有數值完全一樣）。
2. **自動只看最近 20 個交易日。** 20＝法人歷史保存天數（更舊的洞補了法人也會被修剪），大約 4 週，夠蓋過長假期間連續失敗；基準只要抓 1～2 個月，每天多 2 個請求。更舊的洞（像 08-18～08-20）用手動輸入補。
3. **每次最多補 3 天、每個請求間隔 2 秒。** 每天最多多 3×4＋2＋2＝16 個請求，避免被限流；沒補完的下次接著補。
4. **整天全有或全無。** 一天要寫進去，必須上市、上櫃 OHLCV 都夠多檔（上市 ≥500、上櫃 ≥300；正常約 1,090／860 檔），落在法人保存期內的還要兩市場法人都拿到，再加上同期間的除權息事件兩市場都拿到。任何一塊失敗或回空 → 那天一個 byte 都不寫，標「待補」。理由：寧可缺，不要寫半套——半套比缺更難發現。
5. **除權息也要補。** 每日流程是「抓當天除權息事件」，那天失敗事件也漏了（實查 08-18～08-20 dividends.json 是 0 筆，前後幾天每天 5～13 筆）。漏掉事件會讓還原權息算錯，把除息當成真實下跌。
6. **插入正確位置，不是接在最後。** 每檔股票的日期仍保持遞增、不重複；滾動視窗照原規則截（price 每檔 110 天、法人 20 天、指數 110 天、bt_price 500 天）——插進一天就從最舊那頭掉一天。
7. **寫檔順序固定：除權息 → 法人 → 指數 → bt_price → price。** price.json 是判斷「哪天缺」的依據，放最後寫。萬一中途被打斷，price 還沒有那天，下次一樣判成缺口，整天重抓重寫（重寫同一天是覆蓋，不會重複）。每個檔本身是原子寫入，不會寫一半壞掉。
8. **bt_price.json 當下就寫，但只用「插入中間日期」模式**（驗收後改，見下方「驗收後修正」第 1 點）。比 bt 最新日還新的日子不在回補時寫，留給每週合併照原本路徑接上。
9. **失敗安全分兩層。** 網路／資料類預期錯誤（逾時、回空、JSON 壞掉）在每一天各自處理、記待補。非預期錯誤（程式錯誤、官方改格式）由最外層保護殼接住：印完整錯誤訊息、寫進狀態檔 `last_error`，但不往外丟——當天的正常更新、build、部署、TG 照常。程式錯誤靠測試直接呼叫沒有保護殼的 `run()` 抓出來。
10. **連續失敗 10 次就停止自動重試**（例如 TWSE 對某天永久回空，2024-09-24 遇過），列在 `gave_up`，標明「未解決」，不算已處理；手動指定那天會重新給機會。

## 已知限制

- **自動只看最近 20 個交易日**，更舊的洞要手動輸入。
- **基準本身抓不到時那個月不判斷**：FMTQIK 被限流回空，那個月的缺口當天看不到，等基準恢復後才會發現（不會誤判成休市，也不會標成已處理）。
- **「今天」的洞要等明天才補**：只檢查到歷史裡最新那天為止。今天抓失敗時，前端照舊顯示過期警告（fetch_ok 旗標沒動）；明天抓到新的一天後，今天就變成「中間的洞」被補上。
- ~~STOCK_DAY_ALL 回「前一天」的資料卻標 fetch_ok＝True~~：驗收後已處理（見「驗收後修正」第 7 點）。
- **回測權重、層級統計最多晚一週才用到新資料**（每週重算閘門）；想馬上看，手動跑一次並勾 `force_recompute`。成績單、交易日曆、RS、指標每天重算，下一次執行就用到。
- **TWSE 對某天永久回空時**，這支補不了，要改用 `finmind_fill.py --dates`。

## 怎麼確認它有在運作

1. **看 Actions log**：「每日累積最新交易日＋漏抓交易日回補」那步會印 `🩹 漏抓回補：歷史最新 …、基準月份 OK […]；缺口 N 天`，有補就印 `本次補好 N 天 [...]`。
2. **看狀態檔** `pipeline/backfill_state.json`（每天跟著 commit 回 main）：
   - `backfilled`：補過哪些日子、什麼時候補的、上市／上櫃各幾檔、來源（永久累積，方便日後追查）
   - `pending`：還在等的日子、試了幾次、最後一次的錯誤
   - `gave_up`：放棄自動重試的日子
   - `baseline.months_failed`：基準抓不到的月份（有值＝當天沒能完整檢查）
   - `last_error`：非預期錯誤（有值就要找工程師看）
3. **補 08-18～08-20**：見下方「手動補 8 月三天的步驟與預期數字」。

## 驗收後修正（2026-11-13 第二輪）

獨立驗收找到一個會寫壞資料的問題、幾個「失敗了卻看不出來」的問題，這輪全部修掉，每一項都有用假網路的測試。

1. **回測長歷史（bt_price.json）插入舊日期會寫壞序列——已修。**
   白話：bt 是一本「每檔股票從收錄那天起的連續帳」。原本插一天舊資料時，程式會把整本帳重新抄一遍，順便重新審一次「這檔量夠不夠格」，而且那天的資料發給所有股票——包括那天以後才開戶的。結果：晚收錄的 55 檔前面多出 3 筆孤立的舊帳、中間一大段空白；量剛好在門檻邊緣的股票被重審刷掉，整本帳（例如 1565 的 500 天）直接丟掉。
   修法：新增「插入中間日期」模式（`history_store.bt_insert_days`）：只補「已經收錄、而且這天落在它既有起訖範圍內」的股票，不重審、不新增也不刪股票，日期軸照樣維持 500 天（插 3 天＝最舊 3 天滑出）。每週合併（`bt_merge_from_price`）遇到 price.json 裡被回補的舊日期也走同一個模式；比 bt 最新日新的日子才走原本的路。
   實測（真實歷史副本，回補 08-18～08-20）：修前 46 檔多出洞＋9 檔只有孤立 3 列（合計 55）、股票 1481→1465；修後 0 檔多出洞、股票 1481→1481、回補日以外每一格都沒變、再跑一次 6 個檔逐位元相同。
2. **除權息「回 0 筆」不再直接當成功。** 證交所被限流時會回一份「格式正確但沒資料」的回應，跟「那幾天真的沒有除權息」看起來一樣。現在某個市場回 0 筆就記成「未確認」：那幾天這次先不寫價格（維持整天全有或全無——價格寫了、除權息卻漏了，還原權息就會錯，而且之後很難發現），隔天再查一次；**連續 2 次都是 0 筆才接受「確實沒有」**，狀態檔記在 `div_unconfirmed`，接受時在 `backfilled` 那天標 `div_confirmed_empty`。代價：淡季（真的沒有除權息的日子）回補會晚一天。
3. **失敗看得見。** 有錯誤（`last_error`）、有放棄的日子（`gave_up`）、或待補超過 3 天，Actions log 會出現黃色的 `::warning::` 一行白話。另外提供 `gap_backfill.maintenance_hint(state)`，回一行像「資料回補：2 天待補、1 天已放棄（詳見 Actions log）」的字，**還沒接到 TG**（要不要接、接在哪由 Andy 決定）。剛記下的待補（隔天就會補）不會吵。
4. **手動輸入的日期不會被默默丟掉。** 格式錯（例如 `2026/08/18`）或跨超過 3 個月：只略過手動那部分、印黃色警告，**自動檢查照跑**（以前是整個回補一起跳過、還是綠燈）。日期所在月份的官方交易日清單抓不到時，放進 `manual_retry`，之後每次執行再確認一次。
5. **TWSE 卡住不再拖 20 幾分鐘。** 回補的請求改用較短逾時（每個網址最壞約 32 秒，本機實測 31.5 秒），第一個網路錯誤就停掉本次回補、沒做完的記待補；另有 90 秒的整體時間預算（除權息一次 2 個請求，要剩 64 秒以上才開始）。推得的上限：回補這一步最多比平常多約 2 分鐘（90 秒預算＋最後一個請求 32 秒）；只有「今天資料看起來是舊的」那種日子，每日流程會再多查一次交易日清單（最壞再 32 秒）。沒有拆 workflow step。
6. **只有上市、沒有上櫃的日子也抓得到。** 缺口判斷改成分市場：上市至少 500 檔、上櫃至少 300 檔才算「那天有資料」（市場別取自 `universe.json`）。真實歷史檢查過沒有誤報：price.json 110 個完整交易日上市最少 1,076、上櫃最少 842；法人 20 天上市最少 1,070、上櫃最少 747。
7. **官方回舊資料時前端會出現「資料可能未更新」。** 每日抓到的最新交易日比今天舊時，查一次官方交易日清單：清單顯示今天有開盤＝資料過期，`fetch_state.json` 標 `ok:false`（前端既有的過期提示就會出現）。假日、週末、盤中手動觸發不會誤判（官方清單要等當天收盤資料出來才列出今天）；清單抓不到就不判。TG 不受影響（推播用資料日期去重，資料日期沒變就不推）。另外上櫃回空時以前照樣標 `ok:true`，現在也標 `ok:false`。
8. **其他小修**：回補模組改在用到時才載入、載入失敗只印警告不讓每日步驟掛掉；官方回應裡的資料日期跟請求不同就整包不收（實測：證交所個股表標題寫「115年11月11日」、櫃買表內 date 欄是「115/11/11」）；寫完歷史檔、狀態檔卻寫失敗時，回補紀錄已先印在 Actions log，而且因為 price.json 已有那天，下次不會重複回補。

### 還沒處理、要 Andy 決定的
- **每週合併本身就會刪掉「量剛好在門檻邊緣」的股票的整段歷史**（跟回補無關，是原本的設計）：每週重算時把整段 500 天重新審一次平均量 200 張的門檻，掉到門檻下就整檔刪掉。翻 git 紀錄：每週都有 9～22 檔進出，例如下一次每週合併會刪掉 9927（493 天歷史）。回補後多插 3 天真資料，也可能讓幾檔邊緣股剛好跨過門檻被刪（模擬中 1565、1906、3494）。這會讓回測「後來變冷門的股票」整段消失，可能讓勝率偏樂觀。可改成「收錄過的股票不因量縮被刪」，但會改變線上回測數字、檔案也會變大，所以先不動。

## 上線後第一晚該看的訊號

- Actions log「每日累積最新交易日＋漏抓交易日回補」那步有 `🩹 漏抓回補：歷史最新 …、基準月份 OK [...]；缺口 0 天`、`本次補好 0 天；待補 0 天；耗時 X 秒`（X 應在 10 秒以內）。
- **沒有**黃色 `::warning::`（有的話照字面處理：出錯／放棄／卡超過 3 天／手動日期格式錯）。
- 那一步的總耗時只比以往多 10 秒以內；TG 快報正常推一次。
- 當天 commit 的 `pipeline/backfill_state.json`：`last_error: null`、`pending: {}`、`gave_up: {}`、`breaker: null`、`baseline.months_failed: []`；price.json 只多了當天那一列，bt_price.json 沒有因為回補而被改。
- 前端沒有「資料可能未更新」的提示（如果有，看 `fetch_state.json` 與 log 裡「官方清單顯示今天有開盤，但抓到的最新資料仍是…」那行）。

## 手動補 8 月三天的步驟與預期數字

建議：自動模式穩定 2～3 個晚上後再做，不要跟上線同一天。

1. GitHub Actions → 這個 workflow → Run workflow，「手動回補漏抓的交易日」填 `2026-08-18:2026-08-20`，其他都不勾。
2. 跑完看 log 與 `pipeline/backfill_state.json`：
   - 正常情況：`backfilled` 出現 2026-08-18、08-19、08-20，每天 `listed` 約 1,090、`otc` 約 860（驗收時實打 08-19 是 1,091／862）、`div_events` 個位數到二十幾。
   - 如果 log 出現「除權息 … 回 0 列（可能被限流）→ … 先不寫價格」：正常保護，**隔天排程會自動再查一次**（三天在待補佇列裡，不用再手動輸入）；連續兩次都 0 才會接受並寫入。
   - 如果 log 出現「回補斷路器跳開」：TWSE 當下不穩，沒補到的會留在 `pending`／`queue`，之後的排程自動接著補。
3. 寫入後的預期：
   - price.json：這三天各約 1,950 檔（每檔仍是 110 天，最舊的 3 天滑出）。
   - bt_price.json：日期仍是 500 天（加這三天、掉最舊三天）；**股票數不變**；這三天各約 1,385 檔有資料（跟前後一天 1,387～1,389 差不多——只有範圍涵蓋這天的股票才補）。
   - index.json：加這三天（數值取自官方月報，跟既有數值一致）；dividends.json 只多這三天的事件；chip.json 不變（這三天早已超出法人保存的 20 天）。
   - 請求數約 11 個（3 個月份清單、2 個除權息、3 天×2 個行情），一般 1 分鐘內跑完。
4. 補完後回測權重要等下一次每週重算才會用到；想馬上看就再手動跑一次並勾 `force_recompute`。
